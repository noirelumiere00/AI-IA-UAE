1. 全体像（2モード）

モードB：朝メール（プロアクティブ・定時）Phase1 毎朝 各人のGmail＋カレンダーを読み、優先度順ダイジェスト＋下書きをSlack DM。人間は確認/送信のみ。
モードA：対話（オンデマンド）Phase2 Slackで@メンション/DM→ChatGPTの様に会話。社内ナレッジRAGで回答＋資料/提案書生成。

両モードは同一基盤（providers＋MCP＋ナレッジベース＋安全/監査）を共有。出力は自己改善ループに蓄積。

2. 安全の鉄則（最重要・設計の核）

  • 誤送信を「構造的に」不可能化：MCPToolset型に送信系メソッドを含めない＋NeverSendGate二重防御＋test_safetyで機械検証。
  • 自分宛 vs 他人宛の線引き（=「取り返しがつくか／被害の大きさ」）:
宛先例扱い理由
他人(クライアント)返信メール自動送信しない（下書き）信頼を壊す・取消不可
自分会議リマインドDM自動送信OK最悪でも不要通知1回＝可逆

機密データは Bedrock(VPC/IAM) 経由。秘密情報はコミットしない。監査はメタデータのみ・本文非保存。

4. 朝メール処理フロー

  1. 取得：Gmail未読(is:unread newer_than:1d)＋本日のカレンダー予定。重複排除・既存下書き検出。
  2. 分類（2段）：(1)ヒューリスティック(VIP/緊急語/ドメイン)で確信度≥0.8は即採用 → (2)<0.8のみLLMで確定。7カテゴリ＋優先度。
  3. 要約＋抽出：1-2文要約＋トーン。アクション/締切は原文引用必須（推測しない＝ハルシネーション防止）。
  4. 下書き：緊急/プレス等のみ Gmail create_draft（敬語・送信しない）。本文はPIIマスク。
  5. ラベル付け：AIIA/<カテゴリ>。機密はDM限定。
  6. 配信：本日の予定＋優先度順ダイジェストを Slack DM（下書き/プレビュー）。人間が確認。

判断理由

DI一本化(PipelineDeps)SubAgent/AgentContextは型予約のみ＝過剰設計を回避(YAGNI)
