1. 背景・目的・ゴール

  • 背景: 広告PR会社。AWS契約済（Bedrock/Claude利用可）、Claude API利用可、OpenClaw(openclaw.ai)利用可。
  • 課題: 社員の朝のメール確認に時間がかかる（重要度判断・要約・返信下書き・整理が手作業）。
  • 目的: 朝の受信確認を15–20分→2–3分に短縮し、重要案件の見落としをゼロに近づける。安全（誤送信ゼロ）を最優先。
  • 成功指標(KPI)（業界事例§28.4の実測値を反映した具体目標）:
  • K1: 朝の確認所要時間 −70%（15–20分→2–3分）／1通あたり作成 約20分→約5分（−75%）
  • K2: VIPクライアント/プレス案件の見落とし 0件/週
  • K3: 下書き採用率（そのまま/微修正で送信）≥ 50% → 中期「修正なし承認率」70%→90%
  • K4: 分類精度（人手ラベル一致）≥ 90%（CLIENT_URGENT/PRESS_MEDIA は Recall ≥ 95%）
  • K5: 誤送信・情報漏えい 0件（恒久要件）
  • K6: 敬語エラー 月0件（敬語診断スコア ≥ 4.0/5）
  • K7: 監査証跡100%（全下書き/承認に改ざん防止ログ・1年保管：AI事業者ガイドライン準拠）

4. 用語集

  • オーケストレーター: リクエストを適切なサブAgentへ振り分けるメインAgent（本セッション=Claude Codeと同型）。
  • サブAgent: 特定業務を担う子Agent（第1弾=morning_email）。
  • MCP: Model Context Protocol。外部ツール（Gmail/Slack等）を標準化接続。ツール名は mcp__<server>__<tool>。
  • HITL: Human-in-the-loop。人間が最終確認/承認。
  • プロバイダプロファイル: モデルアクセス経路（bedrock / anthropic_aws / anthropic）。
  • 下書き(draft): 送信せず保存される未送信メール/メッセージ。安全境界の中核。

7. 機能要件（FR） ※各に受入基準(AC)

7.1 取得（Fetch）

  • FR-01 既定クエリ is:unread newer_than:1d -category:promotions -category:social でGmail未読スレッドを取得。
  • AC: ページング全件取得。thread_idで重複排除。プロモ/ソーシャルは除外。
  • FR-02 既存下書き検出: list_draftsのthread_id集合で has_existing_draft を付与。
  • AC: 既に下書きがあるスレッドには新規下書きを作らない（FR-15）。
  • FR-03 取得は読取のみ（取得段階で書込みしない）。
  • FR-04 OOO(不在)検出: Gmailバケーション応答が有効なら下書き生成を抑止（設定可）。

7.2 分類（Classify）

  • FR-10 各スレッドを次の排他カテゴリへ分類: CLIENT_URGENT / CLIENT_NORMAL / PRESS_MEDIA / VENDOR_PARTNER / INTERNAL / FINANCE_LEGAL / NEWSLETTER（ルーブリック§11）。
  • AC: ヒューリスティック（VIP送信者/ドメイン/緊急語/List-Unsubscribe）＋LLM構造化出力。confidenceとreasonsを返す。
  • FR-11 VIP（vip_senders/vip_domains一致）は is_vip=True とし優先度を底上げ（§11）。
  • FR-12 低信頼（confidence<閾値）は「要確認」フラグを付け、隠さず提示。

7.3 要約・抽出（Summarize / Extract）

  • FR-20 スレッド毎に1–2文要約＋トーン（neutral/urgent/frustrated/positive/formal）。長文は最新N通＋初回を圧縮。
  • FR-21 アクション項目・質問・明示された締切のみ抽出。各項目は原文引用(source_quote)必須。
  • AC: deadlineはsource_quoteに日付/明示相対表現が含まれる場合のみ設定（pydantic検証で構造的に強制）。推測禁止。
  • FR-22 添付はファイル名/種別のみ列挙（自動処理しない）。5MB超は「メディアレビュー候補」フラグ。

7.4 下書き（Draft）

  • FR-15 draft_categories（既定: CLIENT_URGENT, PRESS_MEDIA）かつ未返信・既存下書き無のスレッドに、簡潔・中立な返信を Gmail create_draft で作成。
  • AC: 送信は絶対にしない（下書きのみ）。本文はredaction後に保存。
  • FR-16 下書きには「未送信・要確認」が明確に分かる旨と、必要に応じ慎重さ喚起（履歴ある重要顧客等）。

7.5 整理（Label）

  • FR-30 カテゴリ別ラベル AIIA/<CATEGORY> を付与（自動 or 確認、設定可）。confidentialラベル付きは公開チャンネルへ出さずDM限定。

7.6 配信（Deliver）

  • FR-40 優先度順 Slack DM ダイジェストを生成し、まず下書き/プレビューとして提示（§13 WF-1）。
  • AC: 既定は slack_send_message_draft。実送信は人間承認フラグが立つ場合のみ。
  • FR-41 ダイジェスト各アイテム: カテゴリ/送信者/1行要約/推奨アクション/締切/下書き有無/Gmailリンク。
  • FR-42 空状態（未読なし）は簡潔メッセージ（§13 WF-2）。大量時はページング/サマリ（WF-3）。
  • FR-43 quiet_categories はダイジェスト本体から畳む（件数のみ表示）。

7.7 起動・スケジュール

  • FR-50 cron（既定 平日07:00、ユーザーTZ）で自動起動。Slackスラッシュ /morning で手動起動。
  • FR-51 --dry-run で副作用ゼロ（下書き/ラベル/Slack送信なし、ダイジェストをstdout）。

7.8 設定

  • FR-60 ユーザー別設定（VIP/無視カテゴリ/TZ/配信先/下書きモード）を反映（§20）。
  • FR-61 プラットフォーム設定でプロバイダ既定・モデル階層を切替（§20）。

7.9 監査

  • FR-70 全イベントをJSONLでメタデータのみ記録（本文/送信者アドレス/下書き本文は保存しない）（§21）。

10. データモデル（pydantic, schemas.py）

class Category(str, Enum):
    CLIENT_URGENT; CLIENT_NORMAL; PRESS_MEDIA; VENDOR_PARTNER; INTERNAL; FINANCE_LEGAL; NEWSLETTER
class EmailMessage(BaseModel): message_id; sender; sender_domain; to:list[str]; subject; date:datetime; snippet; body_text
class EmailThread(BaseModel): thread_id; subject; messages:list[EmailMessage]; has_existing_draft=False; labels:list[str]=[]
class ClassificationResult(BaseModel): category:Category; confidence:float(0..1); reasons:list[str]; is_vip=False
class ActionItem(BaseModel): text; source_quote; kind:Literal["action","question","deadline"]; deadline:datetime|None=None
    # 検証: kind=="deadline" もしくは deadline!=None の時 source_quote 非空必須（推測禁止）
class ThreadSummary(BaseModel): thread_id; one_liner; tone:Literal[...]; action_items:list[ActionItem]=[]
class DraftReply(BaseModel): thread_id; subject; body; rationale
class DigestItem(BaseModel): thread_id; category; priority:int; subject; sender; summary:ThreadSummary; draft:DraftReply|None; gmail_link:str|None
class Digest(BaseModel): generated_at:datetime; user_id; items:list[DigestItem]; counts_by_category:dict[Category,int]
class AgentResult(BaseModel): digest:Digest; drafts_created:int; labels_applied:int; redactions:int; cost_usd:float|None

schemas.py は I/O・SDK import 無し（pipelineの純粋性とテスト容易性を保証）。

11. 分類ルーブリック（カテゴリ判定・優先度）

判定順（先勝ち＋LLMで最終確定）:
1. confidential/法務語＋金融/法務ドメイン → FINANCE_LEGAL
2. VIP送信者/ドメイン一致 → is_vip=True。本文に緊急語(ASAP/至急/deadline/緊急/本日中)あれば CLIENT_URGENT、無ければ CLIENT_NORMAL
3. プレス/媒体ドメイン or 語(取材/interview/掲載/press/記者) → PRESS_MEDIA
4. クライアントドメイン（client_domains） → 緊急語有=CLIENT_URGENT / 無=CLIENT_NORMAL
5. 取引先/パートナー（partner_domains、請求/契約文脈） → VENDOR_PARTNER
6. 社内ドメイン → INTERNAL
7. List-Unsubscribeヘッダ/一括配信特徴 → NEWSLETTER
8. 上記未該当 → LLMが文脈分類、低信頼は「要確認」

優先度(priority, 小さいほど上位): CLIENT_URGENT(0) > PRESS_MEDIA(10) > FINANCE_LEGAL(20) > CLIENT_NORMAL(30) > VENDOR_PARTNER(40) > INTERNAL(50) > NEWSLETTER(90)。is_vip は priority を −5 補正。quiet_categories は本体から除外し件数のみ。

12. プロンプト仕様（prompts.py、structured outputs）

  • CLASSIFY: system=「広告PR会社のメールトリアージ。与えたカテゴリのいずれか1つに分類し、理由を列挙。ヒューリスティックヒントを尊重しつつ本文で確定。推測の断定を避け不確かなら低confidence」。出力=ClassificationResult(json_schema)。モデル=haiku。
  • SUMMARIZE: system=「1–2文で要点。トーン判定。長文は最新の論点と未決事項を保持」。出力=ThreadSummary。モデル=sonnet。長文は最新N通＋初回に圧縮して投入。
  • EXTRACT: system=「アクション/質問/締切を抽出。締切は本文に明示された日付/相対表現のみ。各項目は原文をsource_quoteに引用。無ければ空配列」。出力=list[ActionItem]。モデル=sonnet。
  • DRAFT: system=「簡潔・中立・敬体(敬語)の返信下書き。宛名(様/御中)・定型挨拶(いつもお世話になっております等)・結びを含む日本語ビジネスメール作法に準拠。相手が英語なら英語で。約束や数値を捏造しない。未確定は触れない。署名はユーザー名」。出力=本文テキスト→redaction→create_draft。モデル=opus、effort=high。
  • ※この敬語・メール作法・カテゴリ判定・社内承認フローは Claude Agent Skill として外出しし再利用/標準化（Opt事例§28.1に倣う）。
  • 共通: thinking={"type":"adaptive"}、output_config={"effort":...}、output_config.format（output_formatは使わない）。Bedrockはbudget_tokens/temperature不可。

19. セキュリティ・プライバシー・HITL（詳細）

  • 誤送信不可能(NeverSendGate, 二重防御):
  • Agent SDK経路: can_use_tool で外部送信ツール（Gmail送信/Slack実送信）をDeny、許可は read/create_draft/*_draft/label のみ。
  • pipeline経路: delivery/pipeline は *_draft/create_draft のみ呼ぶ。assert_no_send() で送信系到達時に例外。
  • PIIマスク(redaction.py): カード(Luhn検証)/SSN/AWSキー(AKIA[0-9A-Z]{16})/Bearer・JWT/(?i)(api[_-]?key|secret|password)\s*[:=]\s*\S+ を [REDACTED:<kind>] 置換。適用箇所=下書き本文・ダイジェスト掲載テキスト。
  • 機密ラベル尊重: confidential は公開チャンネル禁止・DM限定。
  • データ所在: 機密メールは Bedrock(VPC/IAM)経由（既定）。秘密情報はenvのみ・yaml非保存。
  • 監査: メタデータのみ（§21）。本文・送信者アドレス・下書き本文は保存しない。
  • 権限: IAMは bedrock:InvokeModel* を許可モデルARNに限定。MCPトークンは最小権限。
  • キルスイッチ: 設定でAgent無効化。Googleカレンダー/不在で一時停止（将来）。
  • 法令準拠（業界調査§28.4）: 総務省・経産省「AI事業者ガイドライン」(2024/4)に従い外部送信はHITL必須、「誰が/何を/いつ/どの情報でレビューしたか」を改ざん防止で記録・1年保管。APPIに従いPIIは外部AIへ渡さない（Bedrock VPC＋redactionで担保）。
  • 多段階承認＋変更履歴（フェーズ1は最小実装→将来拡張）: 下書きは「担当者確認→(対外/高額は)部門長確認→人間送信」。AI原案・修正差分・確認者・時刻を監査に追跡（メタデータのみ）。エスカレーション(24h)・委任は将来。

30.1 CLASSIFY（モデル: haiku）

あなたは日本の広告PR会社のメールトリアージAIです。1スレッドを次のいずれか1つに分類します:
CLIENT_URGENT / CLIENT_NORMAL / PRESS_MEDIA / VENDOR_PARTNER / INTERNAL / FINANCE_LEGAL / NEWSLETTER。
判定規則: ①機密/法務語+金融法務ドメイン→FINANCE_LEGAL ②VIP一致→緊急語(至急/本日中/ASAP/deadline)有=CLIENT_URGENT,無=CLIENT_NORMAL
③媒体/取材語→PRESS_MEDIA ④クライアントドメイン→緊急語で URGENT/NORMAL ⑤取引先/請求/契約→VENDOR_PARTNER ⑥社内ドメイン→INTERNAL
⑦List-Unsubscribe/一括配信→NEWSLETTER。さらに直交属性として priority(緊急/高/中/低)・handling(定型/非定型)・amount_jpy(本文に明示時のみ)・key_person(役職/氏名)を抽出。
重要: 推測で断定しない。不確かなら confidence を下げる。否定表現("〜ではない")を肯定と誤判定しない。出力はスキーマJSONのみ。

出力スキーマ: ClassificationResult{category, confidence, reasons[], is_vip, priority, handling, amount_jpy?, key_person?}

30.2 SUMMARIZE（モデル: sonnet）

スレッドを日本語で1〜2文に要約し、トーン(neutral/urgent/frustrated/positive/formal)を判定します。
長文は最新の論点と未決事項を優先。事実のみ。誇張・推測を加えない。出力はスキーマJSONのみ。

出力: ThreadSummary{thread_id, one_liner, tone, action_items[]}

30.3 EXTRACT（モデル: sonnet）

スレッドからアクション項目/質問/締切を抽出します。各項目に原文を source_quote として必ず引用。
締切(deadline)は本文に日付か明示的相対表現(本日中/今週金曜まで等)がある場合のみ設定し、無ければ設定しない(推測禁止)。
該当なしは空配列。出力はスキーマJSONのみ。

出力: list[ActionItem{text, source_quote, kind, deadline?}]

30.4 DRAFT（モデル: opus, effort=high）

あなたはユーザー本人の代理で、日本語ビジネスメールの返信「下書き」を作成します(送信はしない)。
作法: 宛名(社名+氏名+様/御中)→冒頭挨拶(いつもお世話になっております 等)→用件(簡潔・敬体/敬語)→結び(よろしくお願いいたします)→署名(ユーザー名)。
敬語レベルは関係性(取引先/社内/上司)に合わせる(§39)。相手が英語なら英語で。
禁止: 約束/数値/期日の捏造、未確定事項への言及、誇大表現(「業界唯一」等)。不明点は触れず、確認を促す中立文に留める。
出力は本文テキストのみ(件名は元スレッド踏襲)。

43. マルチユーザー（営業20名）＋認証＋個人別パーソナライズ ★確定

43.1 Gmail/Calendar接続 = 個人別OAuth（3-legged）＋トークン保管(AWS)【変更: DWDは情シス不可】

52.4.2 Skill Registry 我々版（型シグネチャ）

# skills/base.py — 既存 agents/base.py:SubAgent を昇格（後方互換 alias: SubAgent = Skill）
from typing import Protocol, Optional
from pydantic import BaseModel
from aiia.config import UserConfig, PlatformConfig
from aiia.safety.hitl import NeverSendGate

class SkillSpec(BaseModel):
    name: str
    description: str
    draft_only: bool = True          # CIが grep 検証する誤送信ゼロの宣言マーカー
    required_tier: int = 3           # Phase3まで予約（実効は単一Tier=本人分離）
    max_loop: int = 1                # Phase1=1（全同期）。モードAで >1（Bedrock制約内）
    needs_legal_check: bool = False  # Phase3 法令ガードレール適用フラグ（資料/対外Skill=True）

class AgentContext(BaseModel):       # 既存§48.4を踏襲・Phase別に注入を追加
    user: UserConfig
    platform: PlatformConfig
    audit: object                    # AuditLog（既存 safety/audit.py）
    gate: NeverSendGate              # 必須注入＝誤送信ゼロを契約レベルで強制
    kb: Optional[object] = None      # Phase3 RAGClient注入（Phase1-2 = None）
    style_profile: Optional[object] = None  # Phase2 StyleProfile
    conversation_id: Optional[str] = None   # Phase2 モードA
    model_config = {"arbitrary_types_allowed": True}

class AgentResponse(BaseModel):
    ok: bool = True
    needs_review: bool = False       # 失敗分離（§48.2-7）の全Skill共通降格先
    summary: str = ""

class Skill(Protocol):
    spec: SkillSpec
    def run(self, ctx: AgentContext, prompt: Optional[str] = None) -> AgentResponse: ...

class SkillRegistry:                 # Phase1=in-process。depends_onを持たせない＝循環依存が原理的に不可能
    def __init__(self) -> None: self._skills: dict[str, Skill] = {}
    def register(self, skill: Skill) -> None: ...   # draft_only=Falseなら登録時に警告
    def get(self, name: str) -> Skill: ...
    def list(self) -> list[SkillSpec]: ...

  • モデル識別子・実fixture・秘密を成果物に含めない(§48.7/§51 S10・制約5)。
  • Skillにdepends_onを持たせない(フラット登録)。閉路検出問題(既知④)を回避。
  • Tier/Memoryは型予約のみで開始。20人・単一チームでは「本人分離＋単一可視Tier」で当面足りる。

52.9 非エンジニア向け用語解説

  • Skill(スキル): AIにやらせる1つの仕事の単位(例: 朝メール整理、提案書作成)。決まった型に沿って増やせる。
  • Registry(レジストリ): Skillの名簿。登録すると土台を直さずに新しい仕事を追加できる。
  • Protocol/インターフェース: 部品どうしの「約束(差込口の形)」。形が合えば中身を差し替えられ、テストもしやすい。
  • OAuth(3-legged)/PKCE: 各社員が自分のGoogleアカウントで「このAIに読取/下書きを許可」と本人同意する仕組み。会社一括委任のDWDより安全。
  • DWD(ドメイン全体委任): 管理者が会社全体のアカウントを1つの仕組みに委任する方式。我々は不採用。
  • RAG(検索拡張生成): AIが社内資料を検索し、その内容を根拠に答える仕組み。出典を添えられる。
  • ガードレール: 全体を横断する安全装置。誤送信防止・PIIマスク・法令チェックなど。
  • NeverSendGate: 「絶対に自動送信しない」を二重で守る部品。送信は常に人間が最終実行。
  • YAGNI: 「今いらない機能は作らない」方針。必要になってから足す。
  • HITL(人間が最終判断): AIは下書き・提案まで。送信や確定は必ず人間が行う。
  • 監査ログ: 「誰が・いつ・何を確認したか」の記録。本文や個人情報は残さず1年保管。
